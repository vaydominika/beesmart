## 1.1. Application Development

The BeeSmart application was developed as a single Next.js project containing both the React user interface and the server-side application layer. The implementation uses route handlers under `app/api` for data operations, Prisma for MariaDB access, and domain-focused modules under `lib` for shared rules. Client components call the API routes with the browser `fetch` interface, while server-rendered layouts and pages are used where authentication or initial database access is better performed before rendering. The current repository contains no Next.js server actions; all interactive mutations cross the explicit HTTP API boundary.

The subsection structure proposed for this chapter still covers the principal implemented systems. Recently added features, including AI-based publication checks, daily course recommendations, recurring events, activity tracking, private file storage, malware scanning, and scheduled cleanup, fit naturally within the existing sections. The codebase does not contain an implemented email-verification, password-reset email, transactional-email, or notification-email service. The `emailVerified` and `VerificationToken` database fields support authentication-provider compatibility, but no user-facing email workflow uses them at present. Consequently, only the implemented in-application notification system is described below.

### 1.1.1. Authentication, Authorization, and the Core Application Interface

BeeSmart supports account creation with an email address and password as well as Google sign-in when Google OAuth credentials are configured. During password registration, the browser first checks that all fields are present, that the password contains at least twelve characters, and that both password entries match. The registration API repeats validation with a Zod schema, normalises the email address, restricts the permitted lengths, and rejects duplicate accounts without revealing unnecessary account details. Passwords are hashed with bcrypt using a cost factor of 12 before the `User` record is created. After successful registration, the client attempts an immediate credentials sign-in and directs the new user to a personalised first-login dashboard state.

NextAuth coordinates both authentication methods. Its Prisma adapter stores external-provider accounts, while application sessions use signed JSON Web Tokens with a thirty-day maximum age. The credentials provider applies independent rate limits to the normalised email address and the requesting network address before querying the account and comparing the bcrypt hash. A valid token is checked against the database so that a session for a deleted user is invalidated instead of remaining usable until its natural expiry. The login form also preserves an optional callback URL, enabling authentication to return the user to the originally requested protected page.

The rate limiter persists counters in `RateLimitBucket` rather than keeping them in process memory. Its keys combine an operation scope with a SHA-256 hash of the normalised subject, so raw email addresses and client addresses are not stored as bucket identifiers. Creating, incrementing, and resetting a bucket uses unique constraints and conditional updates to handle two simultaneous login or registration requests. The registration route returns rate-limit metadata through standard limit, remaining, and retry headers. Successful authentication clears the email-specific failure bucket, while expired buckets are later removed by the maintenance command.

The JWT callback copies the internal `User.id` into the token only after successful sign-in and validates that identifier on subsequent requests. The session callback then exposes it as `session.user.id`, which becomes the stable ownership key used by route handlers. The shared `getCurrentUserId()` helper loads the authentication module dynamically because `auth.ts` already imports the Prisma client; this prevents a circular static dependency between session resolution and database construction. Google is included in the provider list only when both OAuth environment variables are present, so an incomplete configuration cannot expose a non-functional sign-in option.

Access protection is deliberately applied at several levels. The Next.js request proxy redirects unauthenticated page requests to `/login` and redirects signed-in users away from the authentication pages. The authenticated route-group layout calls `auth()` on the server before it renders the common interface. A small client-side session guard handles session changes after hydration. Finally, each protected API handler obtains the current user identifier independently and returns an unauthorised response when it is missing. This final check is essential because an API can be called directly without navigating through a protected page.

The proxy matcher excludes the NextAuth endpoints, Next.js assets, icons, and public image directories, while applying protection to the remaining application paths. The authenticated layout then nests the settings, dashboard, focus, and layout providers around the selected page. This arrangement separates the initial server-side access decision from browser-managed state. A session that becomes invalid after hydration is handled by `AuthenticatedApp`, whereas an initial unauthenticated request is redirected before protected interface content is rendered.

Authorization depends on the resource being accessed. A course creator may manage a course, whereas other users may read it only if it is published and public, explicitly shared with them, or available through one of their classrooms. Classroom permissions are based on the `ClassroomMember` record: teachers and teaching assistants can create and grade work, while student access is limited to learning and submission operations. File downloads repeat the relevant course, classroom, submission, report, or profile checks. Administrative access is resolved from the signed-in user’s email and the configured `ADMIN_EMAILS` allowlist. The application frequently returns a not-found response for sensitive unauthorised resources so that their existence is not disclosed.

Nested-resource handlers do not authorize solely from the identifier in the URL. They query a lesson through its module and course, an assignment or test through its classroom, and a response through its attempt and question. This prevents a caller from combining individually valid identifiers that belong to different parent records. Role checks are also performed on the server for every mutation even when the corresponding button is hidden in React. Consequently, the client interface communicates available actions, while Prisma query predicates and membership records enforce the actual security boundary.

The reusable course predicate illustrates how several access paths are expressed in one database query:

```ts
export function accessibleCourseWhere(userId: string) {
    return {
        OR: [
            { createdById: userId },
            { visibility: "PUBLIC" as const, published: true },
            { visibility: "INVITATION_ONLY" as const, accessGrants: { some: { userId } } },
            classroomCourseAccessWhere(userId),
        ],
    };
}
```

The authenticated interface is assembled by `AppLayout` and several context providers. The left sidebar contains links to Dashboard, Schedule, Classroom, and Courses, together with the activity streak and utility actions for focus mode, settings, optional early-access feedback, and sign-out. The right sidebar contains the profile entry point, notification centre, compact calendar, and upcoming events. Dashboard, layout, focus, and settings providers keep shared client state available while the user changes pages. On mobile devices, the two sidebars become overlays controlled by a compact header. On wider screens, the left navigation remains inline and the right panel is shown only when sufficient width is available. Course editing and viewing use a wider, focused workspace by hiding surrounding sidebars.

The implementation uses a reusable workspace component set for buttons, form fields, selectors, dialogs, tabs, search inputs, progress indicators, loading states, and empty states. These components centralise keyboard focus styling, disabled states, spacing, and semantic colour variables. Sonner toasts report successful operations and recoverable errors, while page-level states provide retry actions when important data cannot be loaded. This shared interface layer gives the subsequent functional areas a consistent interaction model.

### 1.1.2. Dashboard and Course Discovery

The dashboard is the user’s main overview of learning activity. `DashboardProvider` requests `/api/dashboard` once the authenticated shell loads and makes the result available to the centre content and both sidebars. The server assembles this response from several Prisma queries rather than requiring each dashboard component to load the same information separately. It includes the current user, streak, reminders, active report count, owned courses, enrolled courses, newly discoverable courses, and popularity-based selections. A failed request is retained as an explicit error state with a retry control, and a session-expiry response redirects back to login.

The provider stores `data`, `loading`, and `error` separately and exposes an explicit `refetch()` operation. This lets a successful mutation refresh the shared dashboard without remounting the application shell. The endpoint uses restricted Prisma `select` and `include` structures for each collection, then maps database rows into a shared `DashboardData` response type. Cover paths are converted to protected file URLs and rich descriptions to plain-text summaries during this mapping. This keeps storage details and HTML processing outside the card components.

Courses are divided according to the next useful action. “Your courses” contains resources created by the signed-in user and opens them for editing. “Continue learning” is based on enrolments and completed lesson records. “Finished” contains completed enrolments, while “Discover” lists recent published public courses that the user neither owns nor has enrolled in. “Popular now” orders eligible public courses first by average rating and then by enrolment count. The server calculates course progress as the proportion of lessons with a non-null `completedAt` value and calculates ratings from the related `CourseRating` records. These derived values are returned as card summaries so the browser does not need to reproduce database logic.

The categories are derived from distinct predicates rather than dividing one unfiltered result in the browser. Ownership is based on `createdById`; learning state is based on `CourseEnrollment.completedAt`; discovery excludes both owned and enrolled course identifiers; and popularity is restricted to published public content. Course summaries include aggregate counts and related progress rows, from which the server computes percentages with a zero-lesson safeguard. This prevents category membership and progress values from depending on stale client state.

The dashboard search filters the course collections by title and plain-text description. Rich course descriptions are converted to safe text excerpts before comparison or card display. Each course card combines its cover, description, average rating, progress, and an action suited to the user’s relationship with the course. Learners who have started a course can rate it, while available courses can be reported from the same card. Horizontal course rails preserve the overview layout when several courses belong to a category.

Two daily recommendation cards extend ordinary discovery. “Based on your courses” and “Surprise me” call the recommendation endpoint with different recommendation kinds. Recommendations are unlocked after the user completes at least one course. The server collects a bounded summary of recent completed courses and a bounded set of eligible public candidates, excludes already enrolled and user-owned courses, and asks DeepSeek to choose a course identifier using a Zod-constrained response. The first kind uses completed learning as preference context, while the second asks for a deliberately different subject. One result per user, kind, and UTC day is stored in `DailyCourseRecommendation`, allowing repeated requests to return a cached result. A temporary reservation record prevents two concurrent requests from generating different recommendations, and recent selections are avoided when alternatives exist.

Recommendation generation is implemented as a cache-and-reservation workflow. The compound database key consists of user, recommendation kind, and UTC date. A request first returns a completed record when one exists. Otherwise, it attempts to create or claim the daily record and treats a recent uncompleted record as an in-progress reservation. Only the successful claimant calls the provider. The returned course identifier must belong to the candidate set assembled by the server; an arbitrary or inaccessible model response is rejected. If generation fails, the reservation can be retried instead of becoming a permanent empty recommendation.

The dashboard also connects discovery with motivation and navigation. A deterministic daily welcome message changes by user and local date without requiring another stored record. Meaningful actions are written to `ActivityRecord` using unique deduplication keys, and the same process updates the `Streak` record. The current streak appears in the main sidebar, while recent activity may appear on the user’s profile. This design means that dashboard data reflects completed domain actions rather than arbitrary page visits.

### 1.1.3. Course Creation and Management

The Courses page separates learning and authored resources through tabs and provides search and status filters. The API applies the same access rules as the detail routes and returns each course with its creator, tags, lesson count, linked classrooms, enrolment state, progress, and latest access time. This allows the interface to distinguish owned courses from courses available for learning and to display appropriate actions without exposing inaccessible records.

Before creating a first course, the user completes a guided tutorial. The tutorial is supported by a series of repository images that explain basic course setup, modules, lesson content, syllabus generation, saving, and publication checks. Completion is stored in `UserSettings` and is one-way: reopening the tutorial does not remove the completed state. The creation API also checks this value, so bypassing the client dialog cannot skip the requirement. A new course receives a normalised title, optional rich description, up to three controlled subject tags, a visibility level, an optional cover, and optional attachments. Tags use a predefined set and are connected or created transactionally. Temporary file uploads are claimed in the same transaction as course creation so that the database does not retain a course that refers to unavailable uploads.

Course creation validates file identifiers before persisting their relations. The transaction claims the cover under the cover-image purpose and other files under the course-attachment purpose, validates that each attachment has the intended destination, creates or connects canonical tag records, and creates the course and attachment rows. A claim succeeds only for a clean, unexpired `PENDING` file owned by the requester. If any part fails, neither the course nor the file-state changes are committed. This avoids a partially created course with references to temporary or foreign uploads.

The course builder is divided into an outline sidebar and a lesson editor. The sidebar supports adding, renaming, deleting, collapsing, and reordering modules and lessons. Drag-and-drop operations update the interface optimistically and send normalised order values to dedicated endpoints; if persistence fails, the previous order is restored and the user is notified. A lesson can also be moved between modules. Each route verifies that the referenced module or lesson belongs to the course and that the current user owns the course, preventing identifiers from being combined across unrelated resources.

Ordering is persisted as explicit integer fields rather than inferred from creation time. Reorder requests contain the identifiers in their new sequence, and the server compares the submitted set with the records belonging to the course before assigning normalised positions. Moving a lesson additionally updates its `moduleId`. Stable identifier tie-breakers are used when ordered records are read, so temporarily equal positions still produce deterministic output. The optimistic browser state therefore mirrors a validated server representation rather than becoming the authoritative order.

The lesson editor uses Tiptap with extensions for headings, emphasis, lists, task lists, links, images, code blocks, highlighting, colours, alignment, horizontal rules, and YouTube embeds. Lesson titles, descriptions, lock state, rich content, and attachment visibility can be changed from the builder. Edited content is stored in `contentDraft`, while published content remains in `content`. This separation lets an author revise a published course without immediately changing the learner-visible version. Saving and generation states are shown in the editor, and rich text is sanitised on the server rather than trusting browser output.

The sanitizer parses generated or edited HTML against an allowlist of supported tags, attributes, style values, and URL protocols. It removes unsupported markup, restricts link and media destinations, and adds safe relationship attributes to links that open a new tab. A plain-text conversion helper is used wherever only an excerpt or emptiness check is needed. This prevents a visually empty HTML fragment from satisfying content validation and prevents course cards or AI prompts from receiving raw editor markup unnecessarily.

Publishing is treated as a controlled transition. A local structural audit first requires a course title, at least one module, titled modules, at least one lesson in each module, titled lessons, and non-empty lesson content. If the structure is complete, a DeepSeek-based audit checks topic safety, content safety, and basic readability or accessibility. Its output is constrained to a structured list of blocking issues that can be associated with a particular lesson. If the service is unavailable, publication fails instead of silently skipping the safety gate. When the audit passes, draft lesson content is copied to the published field in the same database transaction that changes the course state. The author receives a publication notification, and the action is recorded in the activity ledger.

Course visibility is implemented independently from publication. Private courses remain limited to their creators. Public courses become discoverable after publication. Invitation-only courses use `CourseAccess` records, which creators can add or remove by registered email address; recipients receive an in-app invitation. Published non-private courses linked to a classroom are also available to members of that classroom. When an invitation-only course is posted to a classroom, access grants are created for its existing members. These rules are centralised in the course-access utilities and reused by course, lesson, progress, and file routes.

From the learner’s perspective, opening an available course leads to enrolment and then to the viewer. The viewer follows the stored module and lesson order, records access and completion in `CourseProgress`, and enforces locked prerequisite lessons on the server. When every lesson is complete, the related `CourseEnrollment` receives a completion time and the user receives a completion notification. Removing a completion mark also removes course completion. Users who have started a course may create or update one rating between one and five stars, with an optional bounded comment; authors cannot rate their own work. Course deletion marks all managed covers and attachments for removal in the same transaction as the database deletion, after which the physical files are purged.

Lesson access is evaluated from the ordered course structure. Creators bypass learner locks, while other users must first satisfy the course-access predicate. For a locked target, the server gathers earlier locked lessons and compares their identifiers with completed `CourseProgress` rows. It returns the blocking lesson identifiers when prerequisites remain incomplete. Completion updates use the unique user-and-lesson key while also storing the course identifier, and the enclosing course state is recalculated from stored progress. Browser manipulation therefore cannot mark an inaccessible lesson or incomplete course as finished.

AI authoring is integrated into the builder rather than implemented as a separate course type. The outline generator accepts pasted source text or a supported uploaded source file, extracts a bounded amount of content, and returns editable modules and lessons. The lesson generator can use an instruction, tone, existing lesson text, and an optional source document to produce a draft. These actions are protected by ownership checks, content limits, daily usage quotas, upload validation, malware scanning, moderation where the route applies it, and output validation or sanitisation. Their shared AI controls are described further in Section 1.1.6.

### 1.1.4. Classrooms and Classroom Features

The classroom library presents classrooms in “Joined” and “Created” groups with text search and role filtering. A user creates a classroom with a name, optional subject, and description. The server generates a unique classroom code and creates the owner’s teacher membership together with the classroom. Other users can join by entering this code; a QR code on the classroom page encodes the same join URL. The compound uniqueness constraint on user and classroom prevents duplicate membership. Joining also grants access to any invitation-only courses already linked to the classroom.

Classroom creation uses a nested Prisma write that creates the classroom and its owner membership atomically, so every valid classroom starts with an administrator. The join handler normalises the supplied code, looks up the classroom, checks the composite membership key, and creates the student membership. In the same workflow it creates missing `CourseAccess` rows for linked invitation-only courses. The QR code contains the ordinary join URL and does not embed a separate credential, so the same authenticated authorization and duplicate checks apply whether the code is typed or scanned.

The classroom detail page is organised into Feed, People, and Grades. The header displays the classroom subject, member and post counts, current role, join code, and management controls. The role stored on `ClassroomMember` is contextual: the same user can be a teacher in one classroom and a student in another. Teachers can edit classroom information and perform owner-level membership management, while teachers and teaching assistants are treated as staff for content and grading operations. Students can read the classroom content and participate through comments, submissions, and test attempts.

The People area loads the member list only after verifying that the requester belongs to the classroom. A teacher can add an already registered user by email, choose the user’s classroom role, change roles, or remove members, subject to owner-protection rules. Adding a member also creates access grants for invitation-only courses already linked to the classroom and creates an in-app notification for that user. The current implementation does not send an invitation email and does not create a pending invitation for an unknown address; the target must already have a BeeSmart account. Role changes and removals are saved directly but do not currently create separate notifications.

The Feed is the central content stream. Staff can publish plain text, photos, course references, materials, assignments, tests, and exams. Posts may be pinned, searched, edited, and deleted according to role and ownership rules. Ordinary post content uses the shared rich-text sanitizer. Attachments are first uploaded as temporary `StoredFile` records and then claimed during post creation. A post response includes only serialised public file metadata rather than storage keys or scanner details.

Feed retrieval is paginated, with a default page size of twenty and a maximum of fifty records. Search is applied to title, content, and author name, and optional type and age-order filters are translated into Prisma predicates. Pinned posts are always ordered before the requested chronological order, with the identifier acting as a stable final key. Related assignments, tests, courses, authors, file counts, and comment counts are selected in the same query so the client can render heterogeneous cards without issuing one request per post.

Assignments and tests are modelled as their own database entities but are connected to the feed through `ClassroomPost`. This prevents important educational data from being stored only as unstructured post text. Editing structured work updates both the owning record and the corresponding post representation. Deleting an assignment or test is routed through its owning endpoint so that submissions, grades, attempts, events, notifications, and files follow the correct lifecycle. A shared helper determines whether a feed item should open or delete a post, assignment, test, or exam.

The post-creation route accepts at most one structured attachment: an assignment, test, or course reference. It derives the final `PostType` from that attachment rather than trusting a conflicting client value. Assignment deadlines, test schedules, attempt limits, short-answer keys, course visibility, and attachment ownership are validated before the transaction begins. The transaction then claims files and creates the specialised entity, calendar event where applicable, questions and answer options, and feed post. This prevents the feed representation from existing without its structured source record.

Users can add comments and one level of replies to ordinary classroom posts. The API first verifies classroom membership and ensures that a reply’s parent belongs to the same public post and is a top-level comment. Comment content is trimmed, required, and length-limited. The feed loads top-level comments newest first and replies chronologically, producing a compact discussion structure without allowing arbitrary cross-post parent identifiers.

Courses can be attached to classrooms from either the classroom or course context. The linking endpoint lists courses that the member is allowed to use and creates a unique `ClassroomCourse` junction record. Staff can therefore reuse standalone course content within a teaching group. Publishing a course post notifies classroom members and records a meaningful activity, while the course’s own visibility and publication rules continue to govern access.

Several secondary effects are intentionally separated from the core post transaction. After a post is stored, the application synchronises a related test event where necessary, creates recipient notifications, and records activity. These independent effects use `Promise.allSettled`, so a temporary notification failure does not discard an otherwise valid classroom post. Database changes that must be atomic, such as creating the structured work and its feed entry, remain grouped in Prisma transactions.

### 1.1.5. Assignments, Submissions, and Grading

Assignments are created by classroom staff through a dedicated modal or structured feed composer. An assignment contains a title, instructions, deadline, time zone, an indication of whether the deadline includes an exact time, optional attachments, and grading settings. A graded assignment must have a maximum point value, while an ungraded assignment does not retain grades or a maximum. The server rejects deadlines in the past and validates the local date and time against the submitted IANA time zone. The conversion performs a round-trip check, which also detects local times that do not exist because of a daylight-saving transition.

The deadline parser converts the submitted calendar date and optional local clock time into a UTC instant while retaining `deadlineTimeZone` and `deadlineHasTime`. Retaining both representations allows the interface to display the deadline in the author’s intended zone and distinguish an all-day deadline from midnight. The round-trip comparison verifies that converting the resulting instant back to the selected zone produces the original local values. Invalid zone names, malformed dates, and daylight-saving gaps are rejected before the assignment transaction starts.

Creation produces an `AssignedWork` record and a connected classroom post. A protected calendar event is then created or updated from the deadline. The event uses the assignment as its source of truth, so editing it directly in the calendar is blocked and the user is directed to the assignment editor. When staff update the title, instructions, deadline, or grading configuration, the feed post and calendar event are synchronised. Relevant students receive an in-app update. If a graded assignment becomes ungraded, existing grades are deleted and graded submission statuses are converted back to submitted or late according to their submission time.

Students open a dedicated assignment page that displays the instructions, due information, attachments, and their own submission. A response may contain text and files. The submission API calculates lateness from the server time and assignment deadline, then creates or replaces the user’s single `Submission` record. Replacement is performed transactionally: new temporary uploads are claimed, old attachment records are removed, and their stored files are marked for deletion. The physical cleanup follows after the transaction. This supports resubmission while avoiding orphaned attachment metadata. Submitting the work also records a deduplicated meaningful activity for the streak system.

The uniqueness of `userId` and `assignmentId` implements one current submission per student and assignment. A resubmission therefore replaces the existing response rather than appending an ambiguous second active submission. The server calculates `SUBMITTED` or `LATE` from its own clock and the stored deadline, ignoring any status proposed by the browser. File replacement follows the same two-stage deletion process as other managed uploads, so a failure to remove physical bytes does not undo the student’s newly committed submission.

The same submissions endpoint returns different data according to role. A student receives only their own submission, private feedback comments, and grade. Teachers and teaching assistants receive submitted work with student identity, attachments, comment counts, and existing grades, together with a list of students who have not submitted. This server-side shaping prevents the browser from receiving other students’ work when the requester has a student role.

Staff can grade only assignments configured as graded. The API verifies classroom staff membership, confirms that the target assignment belongs to the classroom, and restricts the score to the range from zero to the assignment maximum. It then creates or updates the `Grade`, records the grader and grading time, and changes an existing submission to `GRADED`. Feedback is stored with the grade. The student receives an in-app notification containing the awarded score, while the grading action contributes to the grader’s activity record.

Assignment grading changes any matching submission to `GRADED` and upserts the learner’s `Grade` inside one Prisma transaction. A composite uniqueness constraint on learner and assignment guarantees one grade row for that pair, allowing later score corrections without creating duplicates under concurrent requests. Notification and activity helpers run only after the transaction has written the authoritative grade. The gradebook endpoint then projects assignment grades together with assessment attempt percentages into role-specific response shapes.

The Grades tab provides a common gradebook for assignments, tests, and exams. For a student it shows only personal submission status, dates, scores, and feedback. For staff it organises results by work item and student and links to the detailed grading screen. Collapsible sections and horizontally scrollable tables keep the same information usable on smaller displays. Assessment grades use percentages, while assignments retain their explicit point scale.

The data model and student submission query contain support for private comments associated with a submission. Their `submissionId` and `isPrivate` fields distinguish them from public post comments, and the student query is prepared to return them with the submission. However, the current repository contains no API operation or interface for creating these private submission comments. Individual written evaluation is therefore implemented through the `Grade.feedback` field, while submission comments should be regarded as partially prepared rather than a complete user-facing feature.

### 1.1.6. Tests and AI-Based Features

Teachers and teaching assistants can create a test or exam from the classroom feed. The editor supports a title, description, opening and closing times, time limit, passing score, maximum attempts, question order, and point values. Questions may be multiple choice, true/false, short answer, or essay. Choice questions store ordered options with correctness flags, while accepted textual answers are stored separately. Questions and options can be reordered before the assessment is published to the feed. Schedule validation prevents a closing time without an opening time, past schedules, and closing times earlier than opening.

A student can start an attempt only when they belong to the classroom, the assessment is within its opening interval, and the maximum-attempt policy allows it. The server returns an existing unfinished attempt rather than creating a duplicate and assigns a sequential attempt number for a new record. The client derives remaining time from the server-side `startedAt` value, so refreshing the page does not reset a timed assessment. Answers are saved after a short debounce through the response endpoint. That endpoint checks that the attempt, question, and selected option belong to the same test and user. Per-answer, total-text, and request-size limits constrain written submissions.

Attempt identity and timing remain server-controlled throughout the session. Starting an assessment queries previous attempts for the user-test pair and reuses the unsubmitted one when present. A new attempt stores its sequence number and start instant. On each response save, the handler verifies that `submittedAt` is still null and that the question belongs to the assessment. For objective questions, a selected option must also belong to that question. The debounced client reduces request frequency, while the server validations make every individual save safe to repeat independently.

On submission, the server upserts the supplied responses and scores the complete assessment in one Prisma transaction. Multiple-choice and true/false questions are checked against the selected option. Short answers are normalised with Unicode compatibility normalisation, whitespace reduction, trimming, and case folding before comparison with accepted answers. Essays receive zero when blank and otherwise remain without points until reviewed. The attempt receives an immediate percentage only when no manual grading is required. A compact form of the automatic-scoring rule is shown below:

The submission handler treats the stored question set as authoritative when calculating totals. Client-supplied points or correctness values are ignored. Awarded points are summed against the total configured points and converted to a percentage only after every response that requires manual review has been resolved. This distinction prevents a provisional zero for a non-empty essay from being mistaken for a final failing grade. The final `submittedAt` value also closes the attempt against further answer edits.

```ts
if (question.questionType === "SHORT_ANSWER") {
    const learnerAnswer = normalizeShortAnswer(response.responseText ?? "");
    const acceptedAnswers = question.answers
        .map((answer) => answer.answerText ? normalizeShortAnswer(answer.answerText) : "")
        .filter(Boolean);
    const isCorrect = learnerAnswer.length > 0 && acceptedAnswers.includes(learnerAnswer);
    return { isCorrect, pointsAwarded: isCorrect ? question.points : 0, needsManualGrading: false };
}
```

The staff assessment dashboard divides classroom members into completed, in-progress, and not-started groups. It loads each completed attempt with the questions, responses, automatic results, and remaining manual work. Staff can award points and add comments to written responses, after which the server recalculates the total percentage transactionally and notifies the student. Manual grading accepts both essay and short-answer responses, allowing a teacher to override or refine automatically determined textual results.

Manual grading is scoped to a completed attempt in the selected classroom and assessment. The route validates the awarded value against the individual question maximum, updates the response, and recomputes the attempt from all stored response points rather than incrementally adjusting the previous percentage. Recalculation avoids accumulated rounding errors and remains correct when a teacher changes an earlier score. Teacher comments are stored on `TestAttemptResponse`, keeping question-level feedback separate from assignment-level `Grade.feedback`.

AI-assisted grading sends bounded essay context to DeepSeek and requires structured output containing every expected response identifier and its awarded points. Only completed attempts belonging to the selected classroom assessment can be processed. A request is limited to ten ungraded essays, and the question, response, and total-context sizes are bounded before the provider is called. The returned identifiers are checked for completeness, awarded values are clamped to each question’s maximum, and the response points and attempt percentage are written in one transaction. This endpoint applies the generated scores directly and does not generate written feedback; staff can subsequently inspect and adjust the stored grading values through the normal grading interface.

AI can also generate editable assessments from two sources. Staff may paste source text directly in the test-creation dialog, or they may generate from the published lesson content of a course that they own or that is linked to the classroom. The requester selects a difficulty and a question count between one and twenty. The output schema constrains the question types and option structure. Pasted source text is checked before generation, and the result from either generation route is moderated before it is returned. Unsafe generation from course content creates an automated report. The generated assessment is returned as a draft; it does not become classroom work until the teacher reviews and submits it.

The same DeepSeek integration supports course outlines, lesson writing, course publication audits, daily course recommendations, and content moderation. Daily limits are separated into `LESSON_CONTENT`, `SYLLABUS`, `TEST_EXAM`, and `GRADING` categories. General generation categories allow three attempts per UTC day, while grading has a larger limit of thirty-five. The reservation operation uses conditional database updates to remain safe when requests arrive concurrently:

```ts
const incremented = await prisma.aiUsageQuota.updateMany({
  where: { userId, category, periodStart, attempts: { lt: limit } },
  data: { attempts: { increment: 1 } },
});
```

The remaining allowance and reset time are returned in response headers and displayed by reusable AI-usage components. The server stores only quota counters and selected recommendation records; it does not store a general history of user prompts. Content moderation uses a Zod-constrained safety result and fails closed if the provider is unavailable. These boundaries limit cost, prevent unbounded requests, and ensure that generated data still passes through the application’s normal validation and editing workflows.

Each AI route performs authorization and size validation before reserving an attempt, then calls the provider with a task-specific schema and maximum output-token value. Structured results are checked again against application context: recommendation identifiers must be eligible candidates, grading identifiers must match the requested responses, and generated assessment arrays cannot exceed the requested question count. Provider errors are converted to bounded API failures without exposing credentials or raw internal exceptions. Usage headers are attached to successful and handled failure responses so the client can keep its remaining-attempt display synchronized.

### 1.1.7. Calendar, Reminders, and Notifications

The Schedule page combines personal events with assignment and assessment events from classrooms in which the user is a member. It offers weekly and monthly views, date navigation, search, source filters, event selection, and a contextual editor. The API supports explicit date ranges, calendar months, upcoming-event limits, and retrieval of one event. Query ranges and result counts are bounded to prevent an accidental unbounded calendar request. Results are ordered by date, all-day status, time, and user-defined position.

An access predicate selects either events owned by the user or classroom events for a classroom in which the user has membership. Structured work is included only while its corresponding post still exists, preventing deleted or unpublished classroom work from remaining visible through an orphan calendar projection. Explicit range requests are limited to 62 days, upcoming requests to 50 returned items, and their database candidate set to a bounded horizon. The response adds a calculated source, classroom name, reminder summary, and `canEdit` flag for the current requester.

Users can create personal all-day or timed events with a title, notes, colour, and optional daily, weekly, or monthly recurrence. Recurrence is stored once on the base `Event`. When a range is requested, the server expands occurrences in memory and assigns stable virtual identifiers composed of the series identifier and occurrence date. Monthly expansion skips months that do not contain the original day instead of shifting the event. Editing or deleting a virtual occurrence currently affects the base series rather than storing an exception. Recurrence is limited to personal events, and reminders are limited to one-time events; these constraints should be understood as deliberate limits of the current implementation.

Virtual occurrence identifiers are parsed back to the base event before access checks and mutations. For a single-occurrence read, the server expands the relevant date and verifies that the requested virtual identifier is genuinely produced by the recurrence rule. This prevents a caller from fabricating an arbitrary date suffix. Since exceptions are not stored, an edit made from any occurrence updates the base event and therefore the generated series, a limitation the interface must communicate through its series-oriented behaviour.

Assignments and scheduled tests generate protected classroom events. Students may view these events but cannot edit them. Classroom staff can reschedule a test through the calendar, which transactionally updates both the event and the test’s opening and closing values. Removing a scheduled test event clears those times and notifies classroom members. Assignments remain editable only through the assignment interface because their deadline includes time-zone and grading implications. Shared synchronisation modules upsert calendar events whenever structured classroom work changes.

The interface uses optimistic updates for suitable personal-event changes. It applies a change to the visible calendar first, sends it to the API, and restores the previous list with an error message if persistence fails. A lightweight event-sync hook broadcasts changes through both custom browser events and `BroadcastChannel`, and refreshes when the tab regains focus. Consequently, the main schedule, right-sidebar calendar, upcoming list, and event dialogs can reconcile changes made elsewhere in the application or another browser tab.

A reminder belongs to one user and one event. The client sends the intended notification time, calculated event-start moment, and IANA time zone. The server verifies that both times are valid, that the notification is in the future and no later than the event, and that the supplied start is consistent with the stored event. An upsert permits one reminder per user and event. When an event changes, invalid reminders after its new start are deleted and remaining reminder metadata is synchronised.

The reminder endpoint recalculates the stored event boundary and compares it with the client’s claimed event-start instant, preventing stale event dialogs from attaching a reminder to an outdated time. The compound user-event key makes repeated saves update the same reminder. Event edits also refresh the redundant task, date, time, and due-time fields used by the dashboard, and reset or remove reminder state where the new schedule makes the previous notification invalid.

Notifications are persisted in the `Notification` model and divided into General and Classroom categories. Course creation and completion, invitations, reports, classroom posts, new or updated work, grades, and reminders can create notification records. Each record can carry a related entity type, identifier, actor, classroom context, and action URL. The notification centre polls once per minute and again when the window receives focus. Users can mark one item read or unread, mark all items read, and navigate directly to the relevant course, classroom work, report, or event.

Due reminders are materialised when the notification endpoint is requested. The server selects unprocessed reminders whose `notifyAt` time has passed, atomically claims each one by setting `notificationProcessedAt`, and creates the notification in the same transaction. This prevents the polling interface from creating duplicates. If reminder notifications are disabled, due reminders are marked processed without producing messages. This mechanism works while the user has the application open and the notification centre is polling; the repository does not contain a separate always-running reminder worker, push-notification service, or email sender. Therefore, reminders are implemented as in-app notifications rather than guaranteed out-of-session delivery.

Notification reads and state changes are scoped by `userId`. The GET handler materialises due reminders before selecting the user’s notification feed, while PATCH operations can mark one record read or unread or update all of that user’s records. Related entity identifiers and action URLs allow the browser to route a notification to its source without embedding full domain objects in the notification row. Classroom-notification helpers evaluate each recipient’s settings and normally exclude the actor, preventing a user from receiving a message about their own action.

### 1.1.8. Focus Timer, Profile, and Settings

The focus feature is available from the persistent sidebar and remains active as the user moves between application pages. Before starting, the user chooses active and break durations and whether a break should start automatically. `FocusProvider` maintains the active phase, remaining time, running state, and accumulated focus and break counts. The header and draggable floating `TimerWidget` expose the timer without requiring the modal to remain open. The widget can be minimised, paused, resumed, stopped, moved to the next phase, or returned to the state saved when it was paused. A completed active phase either starts a configured break or stops for user input, and break completion returns the session to an inactive state.

Completed phases are sent to `/api/focus-sessions` with a generated completion identifier, duration, type, start, and end. The API validates a maximum duration of two hours, chronological timestamps, and the phase type. `completionId` is unique, making a retry idempotent: if the same client completion is submitted again for the same user, the existing record and updated statistics are returned. Focus counts are loaded from the database when the provider starts. The running timer itself is client-managed, so an active, unfinished countdown is not stored as a database session and is not designed as a cross-device timer.

`FocusProvider` keeps the active phase in React state and a mutable reference containing its completion identifier and start time. A one-second interval decrements the displayed value. When it reaches zero, the provider submits the completed phase and either creates the next break phase or pauses according to the automatic-break setting. Persistence is retried once; a repeated request carries the same completion identifier, allowing the server to distinguish a retry from a separate session. Stopping or manually changing phase clears the unfinished reference, so only completed intervals contribute to stored statistics.

The streak system is driven by the activity ledger rather than the focus timer alone. Course creation, publication, lesson and course completion, assignment submission, test completion, classroom publication, material upload, and grading are examples of qualifying activities. Allowed activity types differ between student and staff contexts. Each action supplies a unique deduplication key; only a newly recorded activity updates the streak. A first activity starts the streak at one, an activity on the following UTC day increments it, repeated activity on the same day leaves it unchanged, and a longer gap resets the current value while preserving the longest streak.

Profile settings allow users to change their display name, avatar, banner, and credentials password. Password changes require the current password and accept a new password between twelve and 128 characters; accounts created only through social sign-in cannot change a local password through this form. Avatar and banner values must originate from temporary profile uploads rather than arbitrary external URLs. Replacing an image claims the new `StoredFile`, updates the unique avatar or banner relation, and marks the previous file for deletion inside a transaction. The public profile uses the stored image endpoints or default assets.

Profiles expose published courses and a recent activity list. A profile owner can always view their own page, while other viewers receive either the profile, a private-profile state, or a not-found state. `profileVisibility` controls the page as a whole, and `activitySharing` separately controls the recent-activity section. Activity items are filtered against resources that still exist and that the viewer can access, preventing a public activity entry from exposing a deleted or inaccessible classroom or course. Links lead directly to the relevant course or classroom post when a safe target can be resolved.

General settings are stored in `UserSettings` and mirrored in browser local storage. The local copy applies appearance and focus defaults immediately and acts as a fallback if the server save fails. Server values are then loaded for authenticated persistence across devices. The available visual themes are Bee, Moon/dark, Flower/pink, and Lake/blue. Further settings control default active and break duration, automatic breaks, reminder notifications, classroom notifications, profile visibility, and activity sharing. A small script in the root document reads the stored theme before React hydration, reducing a visible flash of the default theme.

The settings provider begins from validated defaults, hydrates compatible locally stored values, and then reconciles them with the authenticated API response. Theme changes set a `data-theme` attribute on the document root, allowing CSS custom properties to update the entire component system without rerendering each style definition. The server remains the cross-device source of truth, while local storage provides immediate startup behaviour and resilience during a failed settings request.

### 1.1.9. File Management and Security

One upload system is reused for course attachments, lesson material, post files, submission files, course covers, report screenshots, avatars, and banners. A client first sends multipart data to `/api/uploads` with an explicit upload purpose. The server accepts only a controlled set of extensions, applies purpose-specific size limits, compares the declared MIME type with the extension and detected file signature, and rejects unsafe text bytes. Covers, avatars, banners, and ticket attachments are restricted to suitable image types. Production uploads must then pass a ClamAV stream scan; an infected file is rejected, and a scanner outage returns a temporary service error rather than accepting unchecked data.

Validation is performed on the complete byte buffer before it is written. `file-type` supplies signature-based detection for binary formats, while extension and declared MIME values are compared with the detected result and purpose-specific policy. Text-like files receive additional byte checks. ClamAV communication uses the configured host and port in production; local modes may mark scanning as not required according to environment configuration. Only after validation and scanning does the route create the physical file and its `StoredFile` metadata.

Accepted bytes are written to a private storage root with a random storage key prefixed by the checksum. The database stores the owner, purpose, original name, detected MIME type, logical file type, size, checksum, scan status, state, and expiry. The storage key is validated against a strict pattern and resolved below the configured root, preventing path traversal. In development the root defaults to `.data/uploads`; production requires an absolute durable `UPLOAD_STORAGE_DIR`.

File creation uses a cryptographic checksum and random suffix so identical client names cannot overwrite one another. The original filename is retained only as metadata for display and content disposition; it is never used as the storage path. Storage helpers resolve the generated key against the configured root and verify that the result remains within that root. If database creation fails after bytes are written, the upload handler removes the newly written file to avoid leaving an untracked object.

Uploads initially have the `PENDING` state and expire after twenty-four hours. Creating or updating parent content calls `claimUploads` in the same Prisma transaction. This function requires the correct owner, purpose, unexpired state, and clean scan result, then atomically changes the state to `ATTACHED`. Attachment validation requires exactly one destination, confirms that a lesson belongs to the supplied course, and prevents managed files from duplicating legacy metadata. Replaced or deleted files enter `DELETE_PENDING`; physical deletion occurs after the database transaction so a storage error does not undo valid relational changes.

`claimUploads` first removes duplicate identifiers and loads every requested file under all required conditions. It then performs a conditional bulk update from `PENDING` to `ATTACHED` and requires the number of changed rows to equal the number requested. A mismatch means another request claimed or changed one of the files and causes the enclosing transaction to fail. This compare-and-change pattern makes upload claiming resistant to concurrent submissions without holding an application-level lock.

File access is mediated by `/api/files/[fileId]`. The route never returns a storage path. Instead, it loads the file’s parent context and checks whether the requester owns a pending upload, can access or manage the course and lesson, belongs to the classroom post, owns the submission, is classroom staff, owns the report, is an administrator, or is requesting an allowed profile image. Denied access is returned as not found. Responses use the detected MIME type, a safe content-disposition filename, `private, no-store` caching, and `X-Content-Type-Options: nosniff`. Images, PDFs, audio, and video may render inline; other types are downloaded.

The file route derives authorization from attachment relations rather than trusting an upload purpose alone. For example, a `SUBMISSION_ATTACHMENT` is readable by its submitting student and the classroom staff responsible for the assignment, while a lesson attachment follows the course and lesson access rules. Attached avatars and banners are readable by authenticated users so they can appear in the shared interface; profile-page visibility is enforced by the profile endpoint rather than the file route. The route reads bytes only after this relationship check, reducing both information disclosure and unnecessary file-system access for rejected requests.

Legacy attachment fields remain in the schema for files migrated from the earlier public-upload design. A migration script can inspect and import legacy files into private storage, compute checksums, scan them, create managed-file relations, and optionally remove the old public copies only after successful migration. A separate sanitisation script upgrades stored rich text. These scripts support controlled production migration rather than hiding data conversion inside ordinary web requests.

An external scheduler is expected to run `npm run files:cleanup` periodically. The script marks expired temporary files for deletion, processes a bounded batch of pending file removals, and deletes expired rate-limit buckets. Failures for individual physical files are logged and left pending for a later retry. The application itself does not contain an internal cron daemon, which avoids running the same maintenance loop independently in every web instance.

Security controls extend beyond file handling. Registration and sign-in use database-backed rate-limit buckets keyed by hashed subjects. Rich HTML rendered for classroom posts and lesson content is sanitised through an allowlist of tags, attributes, styles, and protocols, and external links opened in a new tab receive safe `rel` values. Test responses, AI prompts, comments, report text, ratings, and other inputs have bounded sizes where the corresponding route defines a limit. Route handlers scope nested identifiers to their parent course, classroom, test, assignment, or attempt before updating them. Prisma transactions protect multi-record state changes, and unique constraints make operations such as enrolment, membership, course access, submission, attempt numbering, and focus completion idempotent or race-resistant.

Global HTTP headers provide a Content Security Policy, frame protection, MIME-sniffing protection, a restrictive browser permissions policy, referrer controls, cross-origin opener policy, and HTTP Strict Transport Security. Production startup validation requires the database URL, authentication secret and public URL, DeepSeek key, absolute storage directory, and active ClamAV configuration. Together, these controls ensure that security assumptions are checked both when the application starts and when individual requests manipulate sensitive data.

### 1.1.10. Administration and Bug Reporting

BeeSmart uses one `Report` model for user-submitted course reports, optional early-access feedback, and automatic course flags. The course-report dialog offers a controlled list of reasons and optional details. The API verifies that both the course and reporting user exist, requires a non-empty reason, and creates the report and receipt notification transactionally. It does not currently repeat the dialog’s reason allowlist, impose a report-text length limit, prevent self-reporting, or deduplicate repeated reports; these are validation boundaries of the present implementation. Early-access feedback is controlled by the `NEXT_PUBLIC_EARLY_ACCESS_FEEDBACK_ENABLED` feature flag. When enabled, the sidebar opens a feedback dialog in which a user describes the issue and may attach up to five screenshots. The server checks the same feature flag, limits the description to 10,000 characters, claims only image uploads created for ticket attachments, and stores the feedback and receipt notification transactionally.

Feature-flag enforcement occurs on both sides of the boundary. The client omits the feedback entry point when disabled, and `/api/tickets` returns a not-found response under the same configuration. When enabled, attachment identifiers are deduplicated and limited before the transaction claims them with the ticket purpose and validates their report destination. The receipt notification is created in the same transaction as the report, so a successful response always has a corresponding in-app acknowledgement.

The personal “My reports” page lists the signed-in user’s course reports and feedback with their current status, related course, description, screenshots, and update dates. An active-report count is also included in dashboard data and shown near profile utilities. If a reported course is later removed, the report remains because its optional course foreign key is set to null; the interface explains that the course is no longer available. Users cannot view automated moderation records as personal tickets because the user-facing query is limited to the two user-submitted report types.

The administration route is protected separately from the ordinary application shell. The server checks the NextAuth session and confirms that the user’s normalised email is present in `ADMIN_EMAILS`; unauthorised visitors receive a not-found page. The administration interface loads all reports with reporter, reviewer, course, and attachment metadata. It divides them into Course reports and Feedback queues, supports Active and All views, displays counts and case references, and provides a compact light or dark theme. Automated course flags are visibly identified in the report queue.

An administrator can change a report among `OPEN`, `IN_PROGRESS`, `RESOLVED`, and `CLOSED`. The API repeats the administrator check, validates the requested status, and transactionally updates the report’s status, review time, and reviewer. For user-submitted reports, the same transaction creates an in-app status notification linked to the personal report page. Automated course flags do not notify the associated user when staff change their state because the record represents a moderation signal rather than a report submitted by that user.

The update route records `reviewedById` and `reviewedAt` together with the status, preserving who performed the latest review transition. It loads the current report before mutation and creates a user notification only for manual report types. Administrative attachment access is still routed through the protected file endpoint, where the administrator allowlist is checked again. The separate `/admin` page therefore does not create a weaker path around ordinary API and file authorization.

AI moderation contributes to this system in two places. Generated assessment content is checked for educational safety, and course publication uses a more detailed structured audit for unsafe, harmful, unreadable, or incomplete material. Unsafe generated content associated with a course can create an `AUTOMATED_COURSE_FLAG`, which enters the same administrative queue as manual reports. Moderation errors fail closed, preventing unchecked content from being accepted as safe.

The reporting workflow is complete for collection, status tracking, attachment access, and in-app updates, but it is intentionally limited in several respects. The repository contains no administrator comment field, assignment mechanism, outbound email update, or integrated external issue tracker. Early-access feedback also depends on its feature flag and is hidden when disabled. These limitations should be presented as the boundary of the current implementation rather than as developed functionality.
