## 1.1. Application Design

BeeSmart was designed as an integrated web-based learning environment for both structured classroom education and independent study. Its design brings course authoring, learning, assessment, communication, scheduling, and productivity tools into one application instead of treating them as separate systems. The repository follows a modular monolithic approach: the user interface and backend are developed in the same Next.js project, while clear internal boundaries separate presentation components, HTTP endpoints, domain-specific utilities, security functions, and database access. This structure suits the scope of the application because it avoids the operational complexity of several independently deployed services while still allowing individual functional areas to evolve separately.

At runtime, the application can be understood as four cooperating layers. React pages and feature components form the presentation layer; route handlers form the HTTP application boundary; modules in `lib` implement reusable domain policies and infrastructure adapters; and Prisma with MariaDB provides persistent storage. External systems, specifically Google OAuth, DeepSeek, ClamAV, and the private file system, are reached only from the server side. Dependencies therefore generally point inward from framework entry points to shared policies and then to persistence or an external adapter. This is not a formally enforced clean-architecture implementation, since domain modules can use Prisma directly, but it establishes a practical separation that is visible throughout the repository.

### 1.1.1. Backend Architecture

The backend is built on the server-side capabilities of the Next.js App Router. Pages, layouts, and HTTP route handlers are organised under the `app` directory. Route groups separate authenticated application pages from authentication pages without changing their public URLs, and the administration interface is placed in its own route area. The application exposes its data operations through route handlers under `app/api`. These handlers provide a consistent server boundary for the React client components and cover authentication, courses, classrooms, assessments, schedules, files, profiles, notifications, productivity records, reports, and administration. The current codebase does not use Next.js server actions; interactive client components communicate with the backend through these HTTP routes. This makes authentication checks, validation, response codes, and error handling explicit at a common boundary.

The request lifecycle reflects this structure. A browser navigation is first evaluated by the NextAuth-aware request proxy, after which a server layout may perform another session check before rendering a protected route. Interactive data requests are sent as JSON or multipart form data to an API handler. The handler resolves dynamic route parameters, derives the current user from the server session, verifies access to the parent resource, validates and normalises the input, and only then invokes Prisma or a shared domain function. Responses return deliberately shaped data-transfer objects rather than unrestricted database rows. In particular, file storage keys, password hashes, scanner metadata, and unrelated users' submissions are not included in ordinary client responses. This explicit request pipeline also makes status codes such as `400`, `401`, `403`, `404`, `409`, `429`, and `500` part of the application contract.

Responsibilities are divided between route handlers and reusable modules. Route handlers interpret requests, verify the current user, validate the immediate operation, and return an HTTP response. Shared rules and domain operations are placed in the `lib` directory. For example, separate modules define course access, lesson progression, classroom roles, assignment deadlines, test scoring, event recurrence, reminders, notifications, user activity, course recommendations, reporting, file handling, and rich-text security. React context providers manage cross-page client state such as dashboard data, layout state, settings, and the focus timer. This division prevents complex rules from being embedded entirely in page components and allows several endpoints or interfaces to use the same behaviour.

The shared modules fall into two broad groups. Domain-policy modules express rules that should be identical wherever they are used, such as whether a user can access a course, how a short answer is normalised, or how a recurring event is expanded. Infrastructure modules isolate mechanisms such as the database client, malware scanner, file system, rate limiter, AI usage accounting, and environment validation. TypeScript types and Zod schemas define the shapes passed between these layers. This distinction reduces accidental disagreement between endpoints: for example, the same course-access predicate can be used when listing a course, opening a lesson, generating an assessment, or authorising an attachment download.

Prisma forms the data access layer between the application and MariaDB. A generated Prisma client is configured with the MariaDB adapter and exposed through a shared database module. The client is created lazily and retained through a global reference, which avoids creating unnecessary connection clients during development reloads. Route handlers and domain modules use Prisma queries for both retrieval and modification, while transactions group changes that must remain consistent. Examples include associating uploaded files with application records, updating assessment-related data, and changing report review status. Relations, unique constraints, and indexes in the Prisma schema complement the application-level checks by protecting important data associations and commonly queried identifiers. Database migrations provide a versioned history of structural changes and make deployment repeatable.

The schema is organised around related aggregates rather than one generic content table. `Course`, `CourseModule`, and `CourseLesson` define authored learning content; `Classroom`, `ClassroomMember`, and `ClassroomPost` define the teaching context; assignments, submissions, tests, attempts, responses, and grades store assessable work; and events, reminders, notifications, files, reports, settings, activity, and AI quota records provide supporting capabilities. Explicit junction models such as `ClassroomCourse`, `CourseAccess`, and `CourseTag` represent many-to-many associations and allow those associations to carry their own constraints or timestamps. Ordered structures store numeric positions, while composite unique constraints protect identities such as one membership per user and classroom, one progress row per user and lesson, and one reminder per user and event.

Referential actions encode part of the lifecycle design. Dependent learning or classroom records commonly cascade when their owning entity is deleted, whereas a report can retain its historical record after a referenced course is removed by setting the course foreign key to null. Optional relation fields are used where an entity may have several contexts, such as a notification that may refer to a course, classroom, assessment, report, or event. The application supplements these database rules with explicit cleanup for resources that MariaDB cannot manage, especially private files stored outside the database.

Authentication is based on NextAuth. The design supports password-based accounts and, when the required environment variables are present, Google authentication. Passwords are stored as bcrypt hashes, and authentication sessions use signed JSON Web Tokens. A request proxy redirects unauthenticated visitors to the login page, while the authenticated application layout performs a second server-side session check before rendering protected content. API routes also obtain the current user identifier independently rather than relying only on navigation protection. This layered approach is necessary because direct HTTP requests must be protected even when a page itself is inaccessible.

NextAuth uses the Prisma adapter for provider-related account data but configures application sessions with the JWT strategy. The token carries the internal user identifier, and the JWT callback verifies that the corresponding database user still exists. This prevents a deleted account from retaining access until the nominal thirty-day token lifetime ends. The database helper loads `auth` dynamically when it needs the current user, avoiding a static dependency cycle because the authentication configuration itself depends on Prisma. Google is registered conditionally only when both OAuth credentials exist, allowing local credential authentication to remain available in environments without that integration.

Authorization is based on ownership, membership, and context rather than a single global user role. Classroom membership assigns the roles of teacher, teaching assistant, or student within a particular classroom. Route handlers check these memberships before allowing classroom operations, while shared course-access functions distinguish course creators, enrolled or invited users, public-course visitors, and classroom-based access. Administrative access is restricted through a configured list of administrator email addresses. These checks are performed close to protected data operations, including file downloads, so hiding a control in the interface is never the only access restriction.

The authorization design also scopes child identifiers through their parents. A lesson operation searches for the lesson through its module and course; an assessment response is checked against its attempt, question, test, classroom, and user; and a submission is resolved through its assignment and classroom. This prevents a valid identifier from one resource hierarchy being reused in another request. Sensitive access failures often return a not-found result, which avoids confirming the existence of a resource to an unauthorised caller. The user interface applies the same policy for usability by hiding unavailable actions, but the server remains authoritative.

Transactions and database constraints are used together for operations that span several records. Course creation can claim temporary files while creating attachment relations; assignment creation connects structured work to a feed post; grading updates both the grade and submission state; and publishing copies lesson drafts while changing the course status. Concurrency-sensitive operations use conditional `updateMany`, unique keys, or upserts. This pattern is used for rate-limit counters, AI quota reservations, reminder processing, attempt numbering, file claims, memberships, enrolments, and idempotent focus-session completion. The design therefore treats the database as both a storage mechanism and a coordination mechanism for requests that may arrive simultaneously.

The architecture includes several measures for protecting input and uploaded content. Request data is bounded and validated, and registration and sign-in attempts are rate-limited through database-backed counters. Rich text is sanitised according to an allowlist before storage or display, including restrictions on HTML elements, attributes, styles, and link protocols. Security headers are applied centrally through the Next.js configuration. These headers restrict content sources, framing, browser permissions, and MIME-type interpretation. Production configuration is validated before startup so that required database, authentication, AI, storage, and malware-scanning settings cannot be omitted silently.

Files are kept in private server-side storage rather than being exposed directly from a public directory. The database stores their ownership, purpose, detected format, checksum, scan result, lifecycle state, and storage key. Upload validation checks size limits, extensions, declared MIME types, and detected file contents. In production, files are scanned through ClamAV before they can be accepted. A protected download route evaluates the user’s relationship to the relevant course, lesson, classroom post, submission, report, avatar, or banner before returning the bytes. The lifecycle separates temporary uploads from files that have been attached to an application entity and files awaiting deletion. A maintenance script removes expired uploads, retries pending deletions, and clears expired rate-limit records. The deployment design expects this script to be invoked periodically by an external system scheduler.

This lifecycle is effectively a small state machine. New files are `PENDING`, have a finite expiry time, and remain owned by the uploader. A domain transaction can claim them only if their owner, declared purpose, scan status, and expiry are valid; a conditional update then changes them to `ATTACHED`. Replacement or deletion changes them to `DELETE_PENDING`. Physical deletion is performed after the relational transaction and can be retried safely if the file system is temporarily unavailable. This separation prevents an irreversible file-system failure from rolling back a valid database change and avoids attaching the same temporary file to two different records.

AI-assisted operations are isolated behind server routes and supporting modules. The application uses the AI SDK with the DeepSeek provider for lesson and syllabus generation, assessment generation, grading assistance, daily course recommendations, and content moderation. Source documents can be converted to text on the server before being included in an AI request. Input sizes and output sizes are bounded, and category-specific daily usage records prevent unlimited generation. Generated rich text is normalised and sanitised before it is stored. Content moderation uses structured output and fails closed when the moderation service is unavailable; unsafe course content can produce an automated report for administrative review. Keeping provider credentials and prompt construction on the server prevents them from being exposed to the browser and makes the AI provider a replaceable integration point.

AI responses are requested through Zod-constrained object schemas instead of being interpreted as free-form text wherever a structured result is required. The schema restricts generated modules, lessons, questions, recommendation identifiers, audit issues, and grading results to shapes the application can validate. Provider output is still treated as untrusted: identifiers are compared with the requested records, numeric grades are clamped to question maxima, rich content is sanitised, and generated material remains editable before publication. Usage accounting is divided by category and UTC day. A conditional database increment reserves an attempt before the provider call, preventing concurrent requests from exceeding the configured allowance.

The notification design is database-based and remains inside the application. Classroom operations can create notifications for relevant members, subject to each recipient’s preferences. Due reminders are materialised as notifications when the notification feed is requested, with transactional claiming used to avoid duplicate messages. No outbound email service is present in the current repository; email addresses are used for identity, sign-in, invitations to already registered users, and administrative identification. This boundary should be stated clearly because automatic communication in the current design means in-app notifications and scheduled maintenance rather than an email-delivery subsystem.

Automation is consequently divided into request-driven work and externally scheduled maintenance. Reminder materialisation is request-driven and runs when the notification feed is polled. File and rate-limit cleanup is exposed as an idempotent command intended for a platform scheduler. The Next.js process itself does not start an internal cron loop, which avoids duplicate workers when several web instances are running. Delivery guarantees are correspondingly limited: a reminder becomes visible when the user next requests notifications rather than being pushed independently to a closed browser.

Overall, the backend structure supports maintainability by keeping framework entry points small and moving shared policies into focused modules. New route handlers can reuse the same access, validation, security, and persistence functions, while the central Prisma schema provides a consistent view of the data model. At the same time, the modular monolith allows related changes to be implemented and tested within one repository, which is appropriate for a BSc-scale application and leaves clear extension points for future integrations.

The verification strategy follows the same module boundaries. Vitest and Testing Library cover domain utilities, route behaviour, React providers, and interactive components, while MSW is available for HTTP-oriented tests. A separate integration-test configuration targets behaviour that requires broader cooperation, and Playwright scripts support browser-level end-to-end tests. Tests concentrate on access rules, time-zone and recurrence calculations, scoring, rate limits, sanitisation, file validation, synchronisation, and race-sensitive state changes. This makes the most failure-prone policies independently verifiable without requiring every check to pass through the full user interface.

### 1.1.2. Functional Design

BeeSmart was designed to support two complementary learning contexts. A user may participate in a teacher-led classroom or use published courses for self-paced learning. The dashboard connects these contexts by showing owned courses, ongoing learning, completed courses, popular material, and discoverable content. Search and recommendation functions help users find relevant material, while progress, recent activity, and streak information provide continuity between visits.

The functional design is centred on shared entities rather than isolated feature areas. A course is the reusable unit of learning content and can be consumed independently, granted directly to selected users, or linked to one or more classrooms. A classroom supplies membership, contextual roles, communication, assignments, assessments, and a shared gradebook. Calendar entries and notifications project important changes from these areas into the user's personal workspace. Activity, streak, profile, and recommendation features then derive additional value from the same learning actions instead of requiring users to record them again.

Account management provides the entry point to the platform. Users can register with an email address and password or sign in through Google when that option is configured. After authentication, they can update their displayed name, password, avatar, and banner. Personal settings cover appearance, focus-session defaults, notification preferences, profile visibility, and activity sharing. Public profiles are designed to present a user’s published courses and recent learning activity, while the privacy settings allow the owner to limit this information.

The course area supports the complete lifecycle of an independent learning resource. A creator can define basic course information, choose a cover image and visibility level, and organise the material into ordered modules and lessons. Lessons support rich content, drafts, attached files, and optional progression locks. The separate builder and viewer experiences reflect the different needs of authors and learners: the builder emphasises structure and editing, while the viewer emphasises navigation through the material and progress completion. Courses may be private, public, or invitation-only and can also be shared with classrooms. Learners can enrol, continue from their recorded progress, complete a course, rate it, or report unsuitable content. Tags, popularity information, and daily AI-generated recommendations support discovery without changing the basic course structure.

Course design separates visibility, publication, and enrolment because they represent different concerns. Visibility answers who may discover or access the resource; publication determines whether an authored version is ready for learners; and enrolment records an individual learner's participation and completion. Draft lesson content permits continued editing without immediately replacing the published version. Progress is recorded per lesson, which supports resumption and prerequisite checks, while the enrolment provides the course-level completion state. These separate states avoid reducing a complex learning lifecycle to one overloaded status field.

Classrooms provide the collaborative part of the platform. A classroom has a creator, a unique join code, members, and contextual roles. Users can create a classroom, join one with its code or QR-based link, and view separately the classrooms they created and those they joined. Within a classroom, the feed acts as the central communication space. It can contain text or photo posts and structured posts that refer to assignments, tests, courses, or learning material. Public post comments support discussion. The data model also anticipates private comments on submissions, although the current interface and API do not yet provide a complete workflow for creating them; written assessment feedback is currently stored with grades. Teachers and teaching assistants receive authoring and management capabilities, while students receive the controls required to access and complete the published work. Membership and classroom settings remain available to the roles authorised to manage them.

The feed was designed as a common presentation channel rather than the only source of educational data. An assignment or test may appear as a feed item, but its deadline, grading configuration, questions, attempts, and submissions remain in specialised records. This allows the same work to appear in the feed, gradebook, calendar, notification centre, and dedicated detail page without parsing post text. Plain announcements and discussions remain lightweight posts. The distinction gives the classroom one coherent timeline while preserving structured data for assessment and reporting.

Assignments are designed around a deadline, time zone, optional exact time, grading state, and maximum score. Students can submit written content and files, after which the submission state records whether the work is pending, submitted, late, or graded. Teachers can inspect submissions, award scores, and provide feedback. The gradebook brings assignments, tests, and exams into a single classroom-level view. Its contents adapt to the current role: a student sees personal results, while classroom staff can review results across members and open the relevant work for grading.

Time is treated as domain data rather than display-only metadata. Assignment deadlines retain the relevant IANA time zone and whether the author specified an exact time, while assessment schedules use explicit opening and closing instants. Calendar projections remain linked to their source work so protected classroom events cannot diverge from the assignment or test they represent. Personal recurrence is represented on a base event and expanded into virtual occurrences for the requested period. This design keeps one authoritative source for each schedule while still presenting all work in a unified calendar.

The assessment area supports tests and exams with configurable opening and closing times, time limits, passing scores, and maximum attempt counts. Questions may use multiple-choice, true/false, short-answer, or essay formats. Answers are saved during an active attempt, reducing the effect of an interrupted session, and a completed attempt retains responses, awarded points, correctness, and teacher comments. Objective questions can be scored automatically, whereas open responses can be reviewed by teaching staff or processed with AI assistance. Teachers receive an assessment dashboard for completed attempts and can adjust grading where human judgement is required.

AI assistance is designed as support for content creation and evaluation rather than as a separate user area. Course authors can generate an outline from text or a supported source document and can draft or revise lesson material with a requested tone and context. Teachers can generate assessment questions and request assistance with grading written responses. The recommendation function uses completed learning as context when selecting new public courses. Content moderation applies AI to educational safety, while daily limits are shown per functional category so users understand the remaining allowance. The design retains editable content and teacher review points, which keeps generated material within existing authoring and assessment workflows.

Human control is retained at different stages according to the risk of the AI operation. Generated outlines, lessons, and assessments are drafts that an author can revise. Suggested essay scores are stored in the assessment grading context and remain adjustable by classroom staff. Recommendations select only from courses already accessible to the user. Publication moderation acts as a blocking gate, and unsafe generated course-related content can enter the administrative review queue. Thus, the functional design uses AI to accelerate bounded tasks while keeping ordinary ownership, access, publication, and grading rules in force.

The schedule combines personal events with classroom work. Users can view weekly or monthly ranges, search events, filter their sources, and create recurring personal events. Assignments and scheduled assessments are linked to protected calendar entries so that changes made in their classroom context remain reflected in the schedule. Reminders add a user-specific notification time to an event. The notification centre then combines these reminders with classroom updates such as new or changed work, grades, and invitations. Notification preferences allow users to disable reminder or classroom categories independently.

Productivity features are integrated into the application shell. The focus timer alternates between configurable active and break periods, remains available while users move between application areas, and records completed sessions. Meaningful learning and teaching activities contribute to a streak, whose current value is displayed in the main navigation. This design links time management and motivation to actual platform use without making them separate workflows.

File management supports the functional areas that require learning material or evidence. Files can be attached to courses and lessons, classroom posts, submissions, reports, profile images, and course covers. Upload purpose is recorded explicitly so that a temporary upload can only be claimed by an appropriate destination and owner. This shared design gives each feature a consistent attachment process and allows access decisions to follow the permissions of the parent content.

Reporting and administration provide a controlled response to unsafe content and user feedback. Users can report courses and, when early-access feedback is enabled, submit feedback with screenshot attachments. They can follow the status of their own reports in a personal report list. Administrators receive a separate interface that divides course reports and feedback into queues, presents the supporting context and attachments, and allows the review status to move through open, in-progress, resolved, and closed states. Automated moderation flags enter the same reporting model, giving human reviewers a common queue instead of a separate moderation system.

Several functional areas are explicitly state-based. Files move from temporary upload to attached content and later to pending deletion; reports move through a review workflow; submissions distinguish submitted, late, and graded states; attempts distinguish active and completed work; and courses separate draft editing from publication. User actions are enabled according to these states and the current relationship to the resource. Designing these transitions explicitly reduces ambiguous cases, such as editing an assessment after an attempt has started or treating an expired upload as a permanent attachment.

These areas form one coherent platform because they share the same users, learning resources, classroom memberships, files, schedule, notifications, and activity records. A course can be studied independently or distributed through a classroom; an assignment or test becomes both classroom work and a calendar item; completion affects progress, grades, activity, and recommendations. The functional design therefore connects authoring, teaching, learning, and personal organisation while preserving different permissions and views for each context.

### 1.1.3. Frontend and User Interface Design

The frontend is implemented with React and TypeScript within the Next.js App Router. Tailwind CSS provides layout and styling utilities, while reusable primitives based on Radix UI provide dialogs, dropdown menus, scrolling areas, switches, and related interactive foundations. Additional specialised libraries support the rich-text editor, drag-and-drop course organisation, motion, icons, QR codes, and toast notifications. The interface is component-based: pages compose feature components, and feature components reuse a common set of workspace controls. This reduces visual variation between application areas and gives repeated interactions consistent behaviour.

The frontend deliberately combines server and client rendering. Root and route-group layouts run on the server where they can evaluate the session before returning protected content. Interactive workspaces are client components because they require browser state, event handlers, dialogs, drag-and-drop behaviour, timers, and repeated API requests. The authenticated layout nests `SettingsProvider`, `DashboardProvider`, `FocusProvider`, and `LayoutProvider` around the page content. This order makes account preferences, dashboard summaries, the running timer, and sidebar state available throughout navigation without placing all application state in one global store.

Client data is scoped according to how broadly it is reused. Dashboard data is fetched once by its provider because the centre dashboard and both sidebars consume parts of the same response. Feature pages keep local state for records that are meaningful only within that workspace. Server pages perform initial session or resource checks where early rejection is useful. The application does not use a separate client data-query framework; it uses typed local state and the browser `fetch` API, with explicit loading, error, refresh, and rollback behaviour. This keeps the data flow visible but requires shared providers and synchronisation hooks where several components display the same data.

The authenticated application uses a persistent shell with primary navigation on the left, page content in the centre, and contextual information on the right. The left sidebar contains the BeeSmart identity, the current activity streak, and the four principal destinations: Dashboard, Schedule, Classroom, and Courses. Focus settings, general settings, feedback access when enabled, and sign-out are placed below the primary navigation. This separates frequent navigation from utility actions. The active destination is visually marked, and links use route-aware state so that detail pages remain associated with their main area.

The right sidebar provides information that is useful across several areas without requiring a full page change. It combines profile access, the notification centre, a compact calendar, and upcoming events or reminders. On wider screens it can remain visible beside ordinary content. More focused workspaces, including the schedule, course library, course builder, course viewer, profile, and personal reports, use the available width for their central task. The course builder and viewer also remove the left sidebar to reduce distraction and increase the working area. When a focus session is active, its remaining time is shown in the header and a floating timer remains available throughout the application.

Responsive behaviour is part of the shell rather than being left to individual pages alone. Below the mobile breakpoint, the left and right sidebars become slide-in overlays controlled from a compact header. A backdrop provides an obvious way to dismiss them, their width is limited to the viewport, and the central content uses a dedicated scroll area. At intermediate widths, the right sidebar also changes from an inline panel to an overlay when there is insufficient space. Page-specific grids, toolbars, tables, and dialogs then adapt through responsive columns, wrapping controls, horizontal scrolling, or mobile sheet layouts. The schedule illustrates this principle by using a full side panel on large screens and a bottom sheet for event details on mobile devices.

`AppLayout` derives workspace behaviour from the current route. Course authoring and viewing suppress the left navigation, while schedules, profiles, reports, and the course library suppress the right contextual panel to preserve horizontal space. Ordinary pages retain the full three-region composition when the viewport permits it. The layout owns the main scroll container, resets scroll position after route changes, and reveals a back-to-top control only after a threshold has been crossed. These responsibilities are centralised because implementing them independently on every page would produce inconsistent navigation and scroll behaviour.

The dashboard is organised as a starting point rather than an exhaustive control panel. A welcome area and search provide orientation, while horizontal course rails separate owned, ongoing, popular, completed, and discoverable courses. Cards use a repeated structure for title, description, cover, rating, progress, and the next relevant action. Daily recommendation cards and shortcuts support discovery and common tasks without obscuring the user’s current learning. Empty, loading, and error states occupy the same visual regions as their eventual content, which keeps the layout understandable while data is unavailable.

Major work areas follow a shared workspace pattern. Course and classroom libraries use a page heading, primary action, tabs, search, filters, cards, and a meaningful empty state. Classroom detail pages use Feed, People, and Grades tabs, keeping communication, membership, and assessment information distinct within one context. The course builder uses an outline sidebar and a larger editing surface. Modules and lessons can be reordered through drag and drop, and the editor provides structured rich-text controls. The course viewer presents the same hierarchy for consumption and progress tracking. The schedule combines a toolbar, week or month views, and a context panel. This consistency allows users to transfer knowledge from one section to another even when the underlying tasks differ.

Complex interaction components encapsulate their own technical concerns. Tiptap represents lesson and post content as editable rich HTML and is extended with links, lists, task items, images, code highlighting, alignment, colours, and YouTube embeds. The course outline uses `@hello-pangea/dnd` to translate drag operations into ordered module and lesson updates. Radix-based dialogs, switches, avatars, separators, and scroll areas provide accessible interaction foundations, while Sonner centralises transient feedback. The focus timer remains mounted at shell level and uses a draggable floating widget, allowing its client state to survive ordinary route transitions.

Reusable interface components define common buttons, fields, search controls, selectors, tabs, cards, dialog sections, progress indicators, switches, loading states, empty states, and form messages. Shared components use semantic colour variables for surfaces, borders, text, accents, focus states, and feedback states. The theme system can therefore provide Bee, dark, pink, and blue appearances without changing component structure. Classroom, course, dashboard, schedule, profile, and administration areas refine these semantic tokens where a distinct visual context is useful. Barlow Condensed gives the learning interface a recognisable display style, while Geist is used where denser profile or administrative information benefits from a more neutral typeface.

The theme implementation uses CSS custom properties as semantic design tokens. Components refer to meanings such as canvas, surface, muted text, border, focus ring, success, warning, and danger rather than embedding a complete palette locally. Each theme replaces these values at the document level, and compatibility aliases support components that still use earlier token names. The root layout loads Barlow Condensed, Geist, and Geist Mono through Next.js font optimisation. A small pre-hydration script reads the locally cached theme and sets the document attribute before React mounts, reducing the visual flash that would otherwise occur while settings are fetched.

Visual hierarchy is created through large page titles, restrained secondary text, bordered surfaces, rounded cards, compact metadata, and prominent primary actions. Spacing is repeated through common page frames and toolbars. Motion is used for short page-entry transitions, tab indicators, sidebar movement, and small interaction feedback, with reduced-motion alternatives present in relevant components. The overall palette begins with BeeSmart’s warm yellow identity but uses semantic success, warning, information, and danger colours so that status is communicated consistently across themes.

Forms and dialogs are designed around focused tasks such as creating a course or classroom, joining with a code, editing an event, submitting work, grading, changing settings, or confirming deletion. Labels are associated with inputs, destructive actions use explicit confirmation dialogs, and disabled or saving states reduce repeated submission. Validation errors appear near the relevant form or through toast messages, while successful changes receive brief confirmation. Loading spinners, skeleton-like loading regions, retry actions, empty states, optimistic updates, and rollback messages provide feedback during asynchronous operations. These patterns are especially important because most interactive pages communicate with API routes after initial rendering.

Optimistic updates are used selectively where the prior state can be restored, including event changes and ordered course content. The component first updates local state, sends the mutation, and replaces or rolls back the provisional value according to the response. Calendar changes are propagated through custom browser events and `BroadcastChannel`, then refreshed when the window regains focus. Other operations, particularly grading, publication, file claiming, and permission changes, wait for the authoritative server response because their side effects or validation rules are too significant to predict safely in the browser.

Accessibility support is visible in the component structure. Navigation regions and tab lists have descriptive labels, active links expose their current-page state, tabs expose selection, expandable sections expose their expanded state, and icon-only controls include accessible names. Focus-visible rings are used consistently for keyboard navigation. Dialogs include titles and descriptions, decorative icons are hidden from assistive technology where appropriate, and status or validation messages use status and alert roles. Tables are used for grade data where row and column relationships are meaningful, while scrollable containers prevent dense information from breaking narrower layouts.

Accessibility is supported primarily through semantics and interaction states in the implemented components. Native buttons and links are preferred for actionable controls, keyboard focus is visually retained, and Radix primitives supply focus management for modal interactions. Motion is limited to interface transitions and honours reduced-motion rules where they are defined. The repository does not include a documented formal accessibility audit or assistive-technology test report, so these measures should be described as implemented accessibility considerations rather than evidence of full standards conformance.

Role-dependent design is expressed by changing available actions and the depth of information rather than by building unrelated interfaces. Teachers and teaching assistants receive creation, scheduling, member-management, and grading controls where their classroom role permits them; students see submission, attempt, progress, and personal-result actions. Course creators enter the builder, whereas learners enter the course viewer. Administrators use a separate, restrained queue interface with its own light and dark themes, but it still reuses the application’s workspace controls. This approach preserves a consistent visual language while keeping each user’s interface relevant to the tasks they are authorised to perform.

No Figma file, wireframe, or other editable design artefact is included in the repository. The current design evidence is therefore contained in the implemented component system, semantic theme tokens, responsive layout rules, tutorial images, and interaction tests. Together, these elements show that the user interface was planned around a stable application shell, reusable task patterns, responsive workspaces, visible system feedback, and contextual permissions rather than as a collection of independently styled pages.
